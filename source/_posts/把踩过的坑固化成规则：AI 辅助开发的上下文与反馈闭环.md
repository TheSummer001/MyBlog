需求是给运营出一份"月度活跃用户的平均订单额"。表结构在文档里，SQL 骨架在仓库里，我让它在这条基础上加一个时间过滤和一张用户表。

回来的 diff 里有两处我没要求的改动：`LEFT JOIN` 换成了 `INNER JOIN`，`AVG(o.amount)` 被挪进子查询，外面又套了一层 `AVG`。

第一处把口径从"所有注册用户"改成"下过单的用户"，人均订单额上浮了一半多。拿旧口径对一遍就能看出来，错得很显眼。

第二处安静得多。平均的平均不等于总平均，小单用户多的分组被赋予了更高权重，结果偏了几个点，跑数的人半个月后才找过来。三个月里这是第三次，前两次我在会话里纠正过，纠正完就散了，换一个会话它照样这么写。

## 三类错误与 hook 的边界

同类错误反复出现，改法不一样，后果一个比一个隐蔽。

| 错误 | 具体改动 | 后果 |
|---|---|---|
| 聚合不可下推 | 先按用户求 `AVG`，外层再求一次 `AVG` | 平均的平均，分组权重失真 |
| JOIN 类型被改 | `LEFT JOIN` 改成 `INNER JOIN` | 口径从全部注册用户变成有订单用户 |
| 多条 SQL 合并 | 三段查询拼成一段，条件从 `ON` 挪到 `WHERE` | 外连接退化成内连接，空值行被过滤掉 |

为了防这类事，项目里配了 PreToolUse hook，写在 `.claude/settings.json`。写文件、执行命令之前跑一遍检查，拦住没有 `WHERE` 的 `DELETE`、拦住 `DROP TABLE`、拦住往 `core/` 包写文件。上面三类，一次都没拦住。

原因不复杂。hook 拿到的是工具名和入参文本：文件路径、命令字符串、写入内容。它能判断这行 SQL 里没有 `WHERE`，判断不了 `LEFT JOIN` 换成 `INNER JOIN` 之后统计口径变了，口径是业务语义，不在文本里。那条 `AVG` 嵌套在外层看起来完全合法，语法检查、SQL 格式化、静态分析都过得去，它错在语义层。

## 上下文精简与规则分层

一开始的想法是一次写全：项目背景、模块划分、构建命令、命名规范、SQL 规范、日志规范、异常处理约定，三千多 token 的 markdown，SQL 那部分在中间，七行。

毛病有两个，都不显眼。约束和背景混在同一个密度里，模型读完十几段架构说明，再读到"统计类查询保持 LEFT JOIN"，注意力已经用在别的判断上了。它没漏读，是读到了但没当成硬约束。另外那七行写得也不像约束，"注意 join 类型不要改"这句话没有可执行内容，既没说改哪种、也没说为什么不能改。

上下文预算也不是无限的。规则 3.5k token，加一份 schema、三个源文件、几轮历史消息，到第四轮就开始有内容被截。截掉的常常是开头，也就是规则本身。

主文件只留四块：这是什么项目、哪些东西不能动、怎么验证、不确定的时候怎么办。其余全部拆到 `rules/` 目录，按场景加载。

| 内容 | 放哪 | 什么时候进上下文 |
|---|---|---|
| 项目定位、技术栈 | `CLAUDE.md` | 每次会话，常驻 |
| 只读目录、禁止操作 | `CLAUDE.md` | 每次会话，常驻 |
| 验证命令 | `CLAUDE.md` | 每次会话，常驻 |
| SQL 口径与聚合规则 | `rules/sql.md` | 要改 SQL 时加载 |
| 编码规范 | `rules/java-style.md` | 写新类时加载 |
| hook 与脚本说明 | `rules/hooks.md` | 改 harness 时加载 |
| 单次事故的复盘 | `incidents/` | 只在提炼规则时读 |

主文件从三千多 token 压到 800 左右，token 占用降了约 77%（项目内用 tokenizer 数的，不是官方指标）。

```text
# 项目：数据服务平台（Java 21 / Spring Boot 3 / MySQL 8）

不能动
- core/ 下所有文件：只读包，改动走 issue 讨论
- db/migration/ 下所有脚本：由 DBA 提交，不生成

验证
- 单测：./gradlew test --tests "*Sql*"
- 本地依赖：docker compose up -d mysql redis

约定
- 改任何聚合、连接、时间窗口之前，先读 rules/sql.md
- 表结构和字段含义不清楚就问，不要猜
```

"不要猜"这三个字比一整段规范有用。它把不确定时的默认动作从"生成一个看起来对的答案"改成了"停下来问"。

一条规则得回答四件事：什么时候该想起来，错的样子，对的样子，为什么错。缺了第四条，模型只会记住这个形状，换个写法照错不误。

```yaml
id: sql-agg-001
title: 聚合结果不能再求一次平均
scope: ["**/*.sql", "**/*Mapper.java"]
trigger: 修改含 AVG / SUM 的查询
wrong: |
  SELECT AVG(avg_amt) FROM (
    SELECT user_id, AVG(amount) avg_amt FROM orders GROUP BY user_id
  ) t
right: |
  SELECT AVG(o.amount) FROM orders o JOIN users u ON o.user_id = u.id WHERE ...
why: 平均的平均按组加权，小单用户多的一组权重被放大，结果会偏
source: incidents/2026-07-18-avg-pushdown.md
```

写"为什么"是这套东西里最费劲的部分，也是最不能省的部分。只写"不要用 INNER JOIN"，下次它可能改成加一个 `WHERE u.id IS NOT NULL`，还是同一个错。写上"口径是全部注册用户，没下单的也要算进分母"，它才可能把这条推广到 `NOT EXISTS` 和 `HAVING` 上。

`scope` 和 `trigger` 也得写。规则文件越攒越多，不写触发条件，加载的时候只能整篇塞进去，前面压 token 的功夫又白做了。

加载靠两条路。一条是主文件里点名："改聚合、连接、时间窗口之前先读 `rules/sql.md`"，这句话要写得足够具体，模型才知道自己此刻算不算"在改"。另一条是人在提需求时顺手带上，比如"按 rules/sql.md 的口径改这段"。两条都不完美，前者依赖模型判断自己在做什么，后者依赖人记得。

## 规则的沉淀与共享

规则不会自己长出来，得有人把会话里发生的事搬到文件里。

```text
harness/
├── CLAUDE.md                # 常驻，约 800 token
├── rules/
│   ├── sql.md
│   ├── java-style.md
│   └── hooks.md
├── incidents/
│   └── 2026-07-18-avg-pushdown.md
└── index.md                 # 规则总表：状态、最近命中时间
```

流程很短。会话里被纠正，收工前把"错在哪、为什么错、正确写法"写进 `incidents/`，当天不必提炼；第二天回头看，能提炼成规则条的写进 `rules/`，`index.md` 加一行。`incidents/` 比 `rules/` 好写，因为它是一段叙述，不需要抽象。这个顺序有用：先记事实，再抽规则，抽不出来就说明还没想明白，别硬写成条款。

规则进 `rules/` 之后要能被引用。SQL 规则里指向 `incidents/` 的具体那一次，出问题的时候有据可查。

最开始规则只在我本机的 `~/.claude/` 下。换台机器、换个同事，等于没有；我自己重装一次也丢。现在 `harness/` 跟着仓库进 git，规则改动在 PR 里能看到，review 时能拦下写错的规则。这一条比预想的重要：写错的规则会被当成事实执行，比没有规则更难发现。

要挡的东西：本地绝对路径、token、真实库名和表名。示例里用占位符，报错信息里的主机名也删掉。两个会话同时改同一个规则文件会冲突，文件小，手合就行，但得约定一条规则一个位置，别把新规则一律追加到文件末尾。

## 复核分工与收益边界

AI 走查擅长找"和代码库其他部分不一致的地方"：别处都判空，这里没有；别的 mapper 都带租户 ID，这个漏了。这些是模式，它见得比人多。业务口径它没有依据。

| 检查项 | AI 走查 | 人工复核 |
|---|---|---|
| 空值判断、分支遗漏 | 可以 | 抽看 |
| 索引命中、N+1 查询 | 可以 | 抽看 |
| 枚举新增值没处理 | 可以 | 抽看 |
| 异常被吞掉 | 可以 | 抽看 |
| 指标算得对不对 | 不行 | 必须 |
| 主键、状态字段的取值 | 不行 | 必须 |
| 时间窗口含不含边界 | 不行 | 必须 |

指标定义、分母是谁、月初第一天算不算上个月，这些只有写需求和业务方清楚，代码里看不出来。分工落到动作上是：AI 先跑一遍出清单，人对着清单核口径。反过来先逐行读再让 AI 查，既慢又重复。观察了三周，同类 SQL 错误从每周两三次降到偶尔一次，这是翻会话记录看出来的，不是严格的对比实验，样本也不大。

规则目录会自己膨胀。三个月后 `rules/` 四十多条，有重复的、有过期的、有互相打架的。`index.md` 记最近一次命中时间，三个月没被命中过的归档；两条冲突就合并成一条更具体的，别留着让人挑。四十多条里被加载过的不超过一半，没被加载的多半是触发条件太窄，或者对应的代码早就改了。清理比写新规则更花时间，也更没人愿意干。写一条规则大概十分钟，值不值取决于这个错犯过几次：犯一次就写，目录会变成垃圾场；同一类错第三次出现，才值得动手。hook 那层留着管不可逆操作，删数据、改迁移脚本、往只读包写文件，这类事不需要理解语义，模式匹配就够，也是唯一能硬性拦住的一层。

## 总结

1. 上下文不是越多越好。主文件压到八百 token，规范拆出去按场景加载，关键约束才不会被稀释。
2. 规则要写"为什么"。只记错误形状，模型换个写法再犯一次。
3. 被纠正的错当天进 `incidents/`，第二天提炼成规则，落进 git，别留在本机。
4. AI 查模式，人查口径。分工划清楚，走查才有意义。
5. 规则目录要定期清理。膨胀比缺失更难处理。

这套东西和 [把 LLM 放进分析链路](https://blog.tooonran.top/2026/05/08/%E4%BA%8B%E4%BB%B6%E9%A9%B1%E5%8A%A8%E7%9A%84%20ASR%20%E2%86%92%20LLM%20%E2%86%92%20ES%20%E5%9B%9E%E5%86%99%EF%BC%9A%E8%AE%BE%E8%AE%A1%E6%8B%86%E8%A7%A3%E4%B8%8E%E5%AE%9E%E8%B7%B5/) 里那句"编排器管顺序，处理器管幂等"是一类主张：约束要落在结构上。写在提示词里的是建议，配在 hook 和目录里的是边界。规则文件也一样，它只有在被加载、被引用、被清理的时候才起作用。
