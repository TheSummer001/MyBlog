一个常见的失败只要两轮。用户先问会员卡怎么续费，接着追问「它的有效期是多久」。检索器拿到的是「它」这两个字，召回了几篇讲有效期条款的文档，模型照着答了一个不相关的期限。

整条链路里，唯一能把主语补回来的地方是历史。检索器看不到历史，重写器才看得到。

历史也不能全塞。几轮之后请求顶满上下文，延迟跟着涨，旧话题还会把重写带偏。

窗口、摘要、重写，这套东西每个多轮 RAG 最后都会长出来。差别在于三者的边界怎么切，以及被压掉的信息还能不能捞回来。

## 会话存储结构

存和压是两种写入频率。存历史每轮一次，只追加，不能丢信息；压摘要十几轮才一次，有损，输出比输入短一个数量级。把它们塞进同一个 `save()`，压缩逻辑跑在写路径上，用户等摘要那几百毫秒。

分开之后接口也很小：

- `MessageStore`：追加一条、读最近 N 条、按 turnId 判重
- `MemoryCompressor`：读一段被窗口挤出去的消息，写一条摘要

摘要可以异步。它慢一点没关系，用户不等它。这类活放到消息队列里做，和文档入库那套后台链路是同一个思路，[Kafka 文档异步处理](https://blog.tooonran.top/2026/05/12/Kafka%20%E6%96%87%E6%A1%A3%E5%BC%82%E6%AD%A5%E5%A4%84%E7%90%86%EF%BC%9A%E4%B8%8A%E4%BC%A0%E3%80%81%E8%A7%A3%E6%9E%90%E3%80%81%E5%88%87%E5%9D%97%E3%80%81%E5%90%91%E9%87%8F%E5%8C%96%E6%80%8E%E4%B9%88%E8%A7%A3%E8%80%A6/) 里拆阶段的理由在这里同样成立：耗时的部分不该卡在请求上。

区别在于幂等。文档处理按文档 ID 去重就行，摘要要按「覆盖到哪个 seq」去重，否则同一个区间会被压两遍，摘要越压越歪。

三个 key，按会话拆开，都带租户和用户维度。

| key | 类型 | 内容 | TTL |
|---|---|---|---|
| `chat:msg:{tenant}:{user}:{conv}` | list | 消息 JSON，顺序追加 | 7 天，每次写刷新 |
| `chat:sum:{tenant}:{user}:{conv}` | string | 摘要正文 + 覆盖到的 seq | 7 天 |
| `chat:meta:{tenant}:{user}:{conv}` | hash | 标题、最后活跃时间、轮数 | 7 天 |

用 list 不用 hash，是因为 `LTRIM` 能直接按条数截断，读取时 `LRANGE -N -1` 拿最近几条，两行命令解决。hash 做不到这个。

```bash
# 追加一轮；LTRIM 只做兜底，真正的窗口在读取时按 token 算
RPUSH chat:msg:t1:u42:c7b9 '{"turnId":"t-8812","role":"user","content":"它的有效期是多久"}'
LTRIM chat:msg:t1:u42:c7b9 -80 -1
EXPIRE chat:msg:t1:u42:c7b9 604800
```

`LTRIM` 保留 80 条，当保险用，防止异常会话无限长。80 条远大于 4 轮，正常对话碰不到，窗口大小另算。

写入时机上，先写 user 再写 assistant，两条共用一个 `turnId`。生成失败重试时按 `turnId` 判重，不会在历史里留下两条一样的提问。如果先等生成完再一起写，一次超时就把用户的问题也弄丢了，下一轮重写完全接不上。

消息结构：

```java
// 一条消息按"轮"组织，turnId 用于重试去重
public record ChatMessage(
        String turnId,
        String role,          // user / assistant / tool
        String content,
        int tokenCount,
        long seq,             // 会话内单调递增
        Instant createdAt) {
}

// 读取结果：窗口内原文 + 更早的摘要
public record ChatMemoryView(
        List<ChatMessage> window,
        String summary,            // 可能为 null
        long summaryCoveredSeq) {  // 摘要覆盖到的最大 seq
}
```

`tokenCount` 在写入时算好存下来。现算要加载 tokenizer，一轮多花几毫秒，长会话里这笔账不划算。读窗口时直接求和。

## 窗口与摘要

约束落在 token 上。轮数只是它的近似，因为每轮长短差得很远，一条贴了长代码的回答能顶十条短问答。以一个 32k 上下文的模型为例，先算预算：

```text
历史预算 = 上下文上限 - 输出预留 - 系统 prompt - 检索上下文
         = 32k - 4k - 800 - 1200
         ≈ 26k（上限）
```

上限是 26k，但实际不会给到这个数。本地测下来，我把它钉在 2000 到 3000 token 之间，折合 4 到 6 轮。

| 参数 | 取值 | 依据 |
|---|---|---|
| 历史预算 | 2000–3000 token | 再往上，重写和生成的收益都不明显 |
| 单轮平均 | 310 token | 用户 60 + 回答 250，本地样本均值 |
| 折合轮数 | 4–6 轮 | 预算 ÷ 单轮 |
| 截断单位 | 整轮 | 切开 user/assistant，重写会读不懂 |
| 硬上限 | 12 轮 | 超过就强制触发摘要 |

窗口再大，收益很快就没了。旧话题留在上下文里，重写器会把上一轮的实体往新问题上套，这个副作用比多带几轮细节更伤。延迟也是线性的，input 涨一倍，首 token 时间差不多跟着涨。截断必须按整轮，前半句用户问「那个型号呢」，后半句回答里才有型号，只留一半等于留了个悬空指代。

摘要的触发条件两条，满足任一条就跑：被窗口挤出去的消息累计超过 8 条，或者被挤出去的 token 累计超过 1500。不在每轮做，太频繁会把摘要抖动成另一份历史。输入是「旧摘要 + 被挤出的原始消息」，输出是「新摘要 + 覆盖到的最大 seq」。旧摘要每次都参与，所以摘要滚动覆盖整段会话，不会只剩最近一次压缩。

```text
系统：你在压缩一段对话历史，供后续检索改写和回答参考。
输入：
  旧摘要（可能为空）
  待压缩的 N 条消息原文

要求：
  1. 数字、日期、金额、版本号原样照抄，不要概括成"较长时间"
  2. 产品名、型号、人名保留原文，不要替换成"该产品"
  3. 否定句和例外条款保留原句，不要改写成正面表述
  4. 用户明确排除的方案单独一行，标记"已排除"
  5. 正文不超过 300 字

输出：
  摘要正文
  覆盖到的最大 seq
```

要求 1 到 3 是被坑出来的。我第一版 prompt 只写了「简要总结」，跑出来「用户咨询了较长的有效期」，数字全没了，追问的时候照样答错。

各类信息的丢失概率差很多：

| 信息类型 | 丢失后的样子 | 处理 |
|---|---|---|
| 数字、日期、期限 | 「较长的有效期」 | 摘要要求原样照抄，另抽结构化字段 |
| 型号、专名 | 「该产品」「那款」 | 实体列表单独存，不参与压缩 |
| 否定与例外 | 「不包含退款」变成「包含退款条款」 | 否定句保留原句 |
| 已排除方案 | 整句消失 | 单列 constraints 字段 |
| 用户偏好（语气、格式） | 消失 | 不压缩，每次原文带上 |

否定句是最危险的一类。它被改写之后语义反转，而且读起来毫无破绽，模型会很有把握地答错。宁可摘要里留一句原文，也不要让模型去猜。

## 查询重写与历史

排查这类问题，第一步是把重写之后的 query 打出来。很多「检索不准」到这一步就结束了：重写器根本没开，或者开了但没拿到历史，扔给检索器的还是「它」。重写正常工作时，失败的来源通常是另外三种。

| 现象 | 触发条件 | 代价 |
|---|---|---|
| 代词没消解 | 重写时没带上一轮用户原话 | 召回整批跑偏，答非所问 |
| 话题被误带 | 历史里最近几轮换了主题 | 把上一轮的实体套到新问题上 |
| 否定被丢掉 | 用户说「不要带退款的那种」 | 召回全是要排除的那一类 |

第三种最难发现，答案读起来通顺，方向反了。重写的输入也不该是整个窗口，给最近两轮原文，加摘要，加当前问题，就够了。重写 prompt 越长，模型越容易把别的轮次的内容揉进来：第三轮问的事、第五轮问的事混在一起，改出来的 query 看着完整，检索却打偏，日志里表现为「改写结果里出现了用户没提过的词」。[Spring AI 那篇](https://blog.tooonran.top/2026/05/14/Spring%20AI%20%E6%A8%A1%E5%9D%97%E5%8C%96%20RAG%20%E5%AE%9E%E6%88%98%EF%BC%9A%E4%BB%8E%E6%89%8B%E5%8A%A8%E6%A3%80%E7%B4%A2%E5%88%B0%20Advisor%20%E7%AE%A1%E9%81%93%E7%9A%84%E6%BC%94%E8%BF%9B%E4%B9%8B%E8%B7%AF/) 讲的是 `ChatMemory` 和 `CompressionQueryTransformer` 的 API 怎么接，那是管道层面的事，这里关心的是喂给重写器的那段历史从哪来、多长、压缩过没有，API 换了，这层判断不变。

顺序固定成重写 → 检索 → 生成，重写器看到的历史必须和最终生成时看到的一致，否则两段链路对「当前话题」的理解会分叉。重写自己也会失败，LLM 调用超时、返回空、返回的东西和原句差太远，都得有兜底：直接用原 query 检索，同时在生成 prompt 里补一句「用户上一轮在问 X」。答得差一点可以接受，整条链路卡住不行。

## 成本对比与租户隔离

同一套语料、同一个模型，三种记忆策略跑二十轮，本地测试估算：

| 方案 | 第 20 轮 input | 20 轮累计 input | 首 token 延迟 | 丢掉什么 |
|---|---|---|---|---|
| 全量历史 | ≈8.2k | ≈9.9 万 | 2.1–2.6s | 不丢，但旧话题污染重写 |
| 最近 4 轮 | ≈3.2k | ≈6.5 万 | 0.9–1.2s | 4 轮之前的所有细节 |
| 4 轮 + 摘要 | ≈3.5k | ≈6.0 万 | 1.0–1.3s | 数字、专名、否定句的原文 |

口径：系统 prompt 800 token，每轮检索上下文 1200，单轮对话 310（用户 60 + 回答 250），摘要每次输入 1200 输出 300，20 轮里触发 4 次。不是基准测试，换模型、换文档长度，数字会变。有意思的是「4 轮 + 摘要」的累计 token 反而比纯窗口低：窗口外的东西被压成一条 300 字的摘要，比留原文省得多。但摘要本身要花四次调用，折下来钱没省多少。

省的主要是别的东西：上下文不炸，重写不被旧话题带偏，KV cache 命中率更高。二十轮以内只有窗口就够了，摘要的收益要到三十轮之后才看得见，样本不大，别当定论。

会话历史里是用户的原话，可能带业务数据、内部称呼、表单里的金额。串号一旦发生就是事故。

| 风险 | 做法 |
|---|---|
| convId 可枚举，猜到别人的会话 | 服务端生成 UUID，前端只持有索引 |
| 换账号复用 convId 读到别人的历史 | key 里带 userId，读之前校验归属 |
| 多租户串数据 | key 前缀带 tenant，不靠应用层过滤 |
| 消息过期了摘要还在 | 三个 key 同 TTL，写入时一起刷新 |
| 日志与外发 | 不打完整历史；摘要 prompt 先脱敏 |

第二行最容易漏。key 里带了 convId 就以为够，实际上 convId 从哪来、谁校验，决定了它是不是一个凭证。前端生成、后端信任，等于没做隔离。

摘要那条也值得多说一句。压缩意味着把原文送出去，而原文里往往有用户随手贴的东西。脱敏放在压缩之前，别放在之后。

## 总结

1. 追加历史和压缩历史分开写，一个每轮一次、一个十几轮一次，混在一个方法里迟早互相拖。
2. 窗口按 token 算预算、按整轮截断，`LTRIM` 只当保险用，不当窗口。
3. 摘要是有损的，数字、专名、否定句要么原样保留，要么单独抽成结构化字段。
4. 重写只喂最近两轮加摘要，喂整个窗口反而更容易改飘。
5. 会话 key 必须带用户和租户维度，convId 由服务端发，前端手里的值不算凭证。
