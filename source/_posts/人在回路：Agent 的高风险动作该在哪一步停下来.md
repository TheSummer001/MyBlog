本地测试里，Agent 被要求修一个挂掉的集成测试。它读了测试代码，判断断言写得太严，顺手把 `test/resources/seed.sql` 里的数据改了，测试就绿了。

测试本身没问题。那份种子数据另外三个模块也在引用，第二天的用例开始挂，排查到下午才发现是数据被改。

回滚也不轻松：那个文件里本来就有一处没提交的改动，`git checkout` 会把两处一起抹掉，只能对着 diff 一行行还原。

那次之后我给它加了一道必须停下来的关口。

## 动作分级

建议错了，人看一眼还能拦。一旦它自己动手，能拦的那段时间就只剩参数校验和审批窗口，过去了就回不来。

中间差一次确认。补上这一次，问题就从"模型会不会错"变成"它该停在哪一步"。难点在后面这半句。所有动作都停下来问，人很快开始盲点通过；只在大事上停，大事的边界又划不清。

分级依据是"错了之后能不能退回去"，工具名本身说明不了什么。

| 级别 | 典型动作 | 默认策略 | 依据 |
|---|---|---|---|
| L0 只读 | 读文件、grep、查文档、GET 请求 | 自动执行，只记日志 | 不改任何状态 |
| L1 可逆写 | 新建文件、改已提交的文件、格式化 | 自动执行，记 diff | 有版本控制兜底 |
| L2 不可逆 | 删文件、覆盖未提交改动、改数据库、装依赖 | 必须审批 | 还原成本高于确认成本 |
| L3 对外 | git push、发消息、调付费接口、部署 | 必须审批，展示完整参数 | 出去了收不回来 |

L1 的"可逆"带条件：文件得进过版本控制，而且当前改动已经提交。开头那份 seed.sql 就在条件外，它有未提交改动，实际属于 L2。所以级别不能按工具名定，得看参数。同一个 `write_file`，写进 workspace 是 L1，写进 `~/.ssh` 或 `/etc` 是 L3。工具注册表里给的级别只是默认值，参数判定负责往上调，不负责往下调。往下调的权利只留给人。

## 审批插入点

审批插在哪里，代价完全不同。

| 粒度 | 做法 | 误报 | 适合 |
|---|---|---|---|
| 工具级 | 整个 `shell_run` 一律审批 | 高，`ls` 也要问 | 早期版本、高敏环境 |
| 参数级 | 解析参数，命中危险模式才问 | 低 | 常态 |
| 批次级 | 一次并行批次统一审批 | 中 | 批量只读或同质写 |

参数级是主路径。路径越界、危险命令、写网络资源，这三类规则覆盖了大部分实际情况：

```java
// 判定只给三档，业务逻辑不要塞进策略里
Decision decide(ToolCall call, PolicyCtx ctx) {
    ActionTier tier = registry.tier(call.name());
    if (tier == READ_ONLY) return ALLOW;

    // 参数级：路径越界比工具名更能说明问题
    for (String raw : call.pathArgs()) {
        Path p = ctx.workspace().resolve(raw).normalize();
        if (!p.startsWith(ctx.workspace())) return NEED_APPROVAL;
    }
    if (tier == IRREVERSIBLE || tier == EXTERNAL) return NEED_APPROVAL;

    return ALLOW;   // L1 且路径落在工作区内
}
```

批次级有个坑：审批界面展示的是整批合集，人得看清"这四个动作分别是什么"。只写"4 个写操作"等于没给信息，人只能盲批。

这条对应并行执行那套批次调度（[一次并发 4 个工具调用：Agent 的并行执行引擎](https://blog.tooonran.top/2026/03/11/%E4%B8%80%E6%AC%A1%E5%B9%B6%E5%8F%91%204%20%E4%B8%AA%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8%EF%BC%9AAgent%20%E7%9A%84%E5%B9%B6%E8%A1%8C%E6%89%A7%E8%A1%8C%E5%BC%95%E6%93%8E/)：一批四个调用，一个审批得覆盖全部，否则一个批次能弹出四次确认。

前提是这一批同质。混了只读和对外调用的批次，拆开单独审批，别图省事。

## 审批协议与超时

回应就三种，协议我定成这样：

```json
{
  "approval_id": "ap_7c31",
  "session_id": "s_2026",
  "tool_call_id": "call_9f2",
  "decision": "edit",
  "edited_args": {"path": "src/main/java/.../PageQuery.java"},
  "reason": "只改这个文件，别碰 OrderJob",
  "decided_by": "local-user",
  "decided_at": "2026-05-19T22:41:07+08:00"
}
```

edit 最有用，也最容易做错。人改完参数之后必须重新走一遍参数校验和分级判定，手改也可能越界；更不能因为"人已经批过"就跳过校验。批准的是那组参数，不是这个工具。

deny 必须带原因，原因要进 observation。只回一个 `denied`，模型会理解成"这次不行，换个写法再试"，本地那轮它连着试了三种不同命令去删同一个目录。改成"用户拒绝：不允许删除该目录下的文件，如需确认，请先列出目录内容"，它才真的转向。

这条细节决定 deny 有没有用。拒绝信息里带上"为什么"和"替代做法"，比只给一个布尔值强得多。

超时默认按 deny 处理这个动作，任务继续往下跑，除非这一批里有 L3。三个理由：

- 无限等会把进程挂住，晚上没人看就一直挂着
- 中止整个任务代价大，人回来还得从头跑一遍
- L3 不同，不确定有没有发出去，继续跑会叠加不可控的效果

L3 超时按中止处理，该动作标 `UNKNOWN`，等人回来决定。

窗口给 10 分钟，界面上带倒计时和这一批剩下的动作数。

非交互场景（CI、定时任务）不发起审批，没人能点。这类环境要在启动时就把策略定成"命中即拒绝"，别跑到一半才发现卡在那里等一个不存在的点击。

## 状态恢复与审计

长任务跑几个小时，进程重启是常事。审批状态必须落库。

| 状态 | 含义 | 重启后怎么办 |
|---|---|---|
| PENDING | 已发起，等人 | 重新展示给人 |
| APPROVED | 批了，还没执行 | 校验 args_hash 后执行 |
| EXECUTING | 正在执行 | 标 UNKNOWN，交给人 |
| EXECUTED | 执行完 | 禁止重放 |
| DENIED | 人拒了 | 写进 observation，不重试 |
| EXPIRED | 超时 | 按 deny 记 |

持久化字段：approval_id、session_id、tool_call_id、args_hash、tier、status、created_at、expires_at、decided_by。

EXECUTING 这一档是关键。进程在工具执行到一半崩掉，这个动作到底做没做，谁也说不准。自动重试是最差的选择，push 和发消息重放一次就是两次。所以标 UNKNOWN，下次启动列进待确认清单，让人看一眼实际状态。

恢复时先对 args_hash。人批的是那组参数，上下文变了之后重放同一组参数，未必还是人想批的东西。

日志要能回答一个问题：这个文件是谁、在哪个审批下、被改成什么样的。

| 字段 | 说明 |
|---|---|
| trace_id / session_id / node_id | 串起会话和 DAG 节点（[从 ReAct 到 Plan-and-Execute：把任务拆成 DAG](https://blog.tooonran.top/2026/04/25/%E4%BB%8E%20ReAct%20%E5%88%B0%20Plan-and-Execute%EF%BC%9A%E6%8A%8A%E4%BB%BB%E5%8A%A1%E6%8B%86%E6%88%90%20DAG/)） |
| tool_call_id + args_hash | 对回具体调用，参数脱敏后取哈希 |
| action_tier / matched_rule | 命中的哪条策略，方便回看规则 |
| decided_by / decided_at | 谁批的、什么时候批的 |
| approved_args_diff | edit 改动了哪些参数 |
| exec_status / duration_ms | 执行结果和耗时 |
| output_digest | 产物摘要，不存全文 |

参数原文不写日志。里面有 token、连接串、用户数据，日志系统一般比文件系统松，写进去就是个漏点。

决策时间和执行时间分开记。中间隔着的那段就是人在考虑，如果大量审批几十毫秒就通过，说明人在盲点，规则该收紧或者往上提一级。

## 兜底分工与审批疲劳

| 手段 | 挡住什么 | 挡不住什么 |
|---|---|---|
| 人工审批 | 意图错误 | 人疲劳之后随手点通过 |
| 沙箱 | 命令的爆炸半径 | 工作区内的误改 |
| 可写目录白名单 | 越界写入 | 白名单内的错误用法 |
| 只读挂载 | 改配置、改凭证 | 读出来再发到外部 |
| 危险命令黑名单 | 已知的 rm -rf、dd | 变形写法、脚本间接调用 |

最硬的是沙箱和只读挂载，因为它们不依赖任何判断。审批管的是"这次要不要做"，沙箱管的是"做了最多能坏到哪"。黑名单只能当减速带。命令是字符串，变形写法太多，拿它做安全边界迟早漏。我本地只拿它拦手滑，真环境靠容器加只读挂载。顺序上还有一处容易搞反：参数校验放在审批之前还是之后。我选之后。人改过的参数需要重新校验，校验要是放在前面，人把路径改到外部目录照样能过。

一道审批值不值，取决于它弹出的频率。十分钟弹三十次，人从第三次开始就不再读内容。本地连续跑一批任务，命中审批平均每个任务 6 次，其中 4 次是同一类"写工作区内文件"。这类审批基本被无脑放过，只增加了操作量。

处理办法是把它降级成 L1：工作区内的写，加 git 快照，自动执行。真正需要停的是越界写、删除、对外动作。如果暂时降不了级，还有个折中：同一会话里对同一工具、同一参数范围批准一次，后续在一段时间内复用。复用要有边界，参数 hash 变了就重新问，时间窗过期也重新问。还有一条：定期统计审批记录里"决策耗时小于一秒"的比例。这个数超过一半，说明规则该重做了，那时候的审批已经退化成一个形式。

## 总结

1. 分级看"错了能不能退回去"，不看工具名。同一个 write_file 写到不同路径，级别不一样。
2. 参数级审批是常态，工具级只适合早期或高敏环境，批次级必须展示整批明细。
3. deny 要带原因和替代做法，只回一个拒绝标记，模型会换个写法重试。
4. edit 之后重跑校验，批准绑定的是那组参数。
5. EXECUTING 状态下崩溃标 UNKNOWN，不要自动重试。沙箱和只读挂载是最后一道，黑名单算不上边界。
