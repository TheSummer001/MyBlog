一份六十多页的设备操作手册，问"超过 90 天的历史数据怎么归档"。答案在第 12 页，一张表，加表下面两行说明。

检索返回的前 8 条里没有它。第 3 条讲的是归档权限，第 7 条是一段备份命令。看起来都沾边，都不是答案。

把原文捞出来对着看，那块内容被切成了三份：表格标题落在上一块末尾，表体自己一块，表下面那两句说明跟在下一节的开头。切块阈值设的 500 字符，正好切在那个位置。

## 切块粒度与召回

那批失败的问题一共 40 条，其中 12 条召不回来。对着原文一条条标位置，有 8 条答案落在块的边界附近，或者被拆进了两个块。

剩下的 4 条是另一个问题：问法和文档用词对不上。这两类问题经常被混在一起讨论。嵌入模型换一个、加个 reranker，是能改善排序，但候选里没有那块内容，重排也无从下手。检索只能在已有的块里找。

把 12 条按失败位置分堆，调参的方向就分开了：边界附近那 8 条动切块和重叠，问法对不上的 4 条动嵌入模型。混在一起看，容易得出「切块整体不行」的结论，把本来合适的参数改掉。

块切错了，后面每一层都只能替它兜着，兜不住的部分最后落在用户面前。

粒度是有代价的，往两头调都会掉东西。

| 块大小 | 召回粒度 | 上下文完整性 | 索引成本 | 常见表现 |
|---|---|---|---|---|
| 128–256 token | 很细 | 常常缺主语和前提 | 最低 | 召回一堆碎片，模型拼不出完整答案 |
| 512 token | 适中 | 一般够一段论述 | 中 | 大多数场景的起点 |
| 1024 token | 偏粗 | 一节讲完 | 偏高 | 一块混了三个主题，排序被平均掉 |
| 整节 | 最粗 | 最完整 | 取决于文档 | 短节浪费额度，长节顶满上下文 |

块太小的时候，嵌入向量本身没有足够的信息。一句话里全是"归档""权限""备份"这类词，几十个块在向量空间里挤成一团，谁排前面靠运气。

块太大的时候反过来。一个向量要概括三四个主题，余弦相似度被摊薄，本来该排第一的块掉到十来位。

判断标准落不到具体数字上，只能落到文档上：一个块应该能独立回答一个问题。翻译成可操作的形式，就是三件事。

- 带得上它所在的小节标题
- 装得下完整的表格和表格的说明
- 不把一条条款切成两半

拿这三条回头看开头的例子：表格标题、表体、说明各自成块，没有一块能独立回答问题。阈值本身不用动，只要切的时候认得出这三段属于同一张表，500 字符就不会落在那儿。

粒度还要跟着文档类型走。手册和制度一段讲一件事，512 的块能覆盖多数段落；合同的一条条款牵动整节，块得按条款给。同一个索引里混着两类文档，参数就得按 `docType` 分派，一套切到底的方案覆盖不了两种结构。

## 三种切法的成本

| 切法 | 实现成本 | 适合的文档 | 主要问题 |
|---|---|---|---|
| 固定长度 | 最低，一个参数 | 会议纪要、新闻、OCR 后的纯文本 | 不问语义，切在哪算哪 |
| 按结构 | 中，依赖解析质量 | 手册、制度、合同、技术规范 | 文档没结构时退化成固定长度 |
| 按语义 | 高，每句都要算向量 | 长论述、无标题的连续文本 | 阈值难定，块大小不可控 |

固定长度是最省事的办法，`chunk_size` 加 `chunk_overlap` 两个参数就能跑。它的问题在于对内容一无所知：可能把"如下表所示"和数据表切开，也可能把一句话的宾语留在下一块。

按结构切，收益主要来自文档本身。企业文档里大部分是手册、制度、合同，有编号、有标题层级、有条款序号。这些结构是写文档的人替你标好的语义边界，不用白不用。

按标题切的骨架大概长这样，重点是顺手把章节路径记下来，后面拼进检索文本。

```java
public class HeadingTextSplitter {

    public record Chunk(String sectionPath, String content, int order) {}

    private final int maxChars;

    public HeadingTextSplitter(int maxChars) {
        this.maxChars = maxChars;
    }

    public List<Chunk> split(Document doc) {
        List<Chunk> blocks = new ArrayList<>();
        Deque<String> path = new ArrayDeque<>();   // 当前章节栈
        StringBuilder buf = new StringBuilder();

        for (String line : doc.getText().split("\n")) {
            int level = headingLevel(line);
            if (level == 0) {
                buf.append(line).append('\n');
                continue;
            }
            flush(blocks, path, buf);
            while (path.size() >= level) {
                path.removeLast();
            }
            path.addLast(line.substring(level).trim());
        }
        flush(blocks, path, buf);

        // 超长小节再按空行二次切，章节路径复制到每一块
        return blocks.stream()
                .flatMap(b -> splitLong(b, maxChars).stream())
                .toList();
    }

    private int headingLevel(String line) {
        int level = 0;
        while (level < 4 && level < line.length() && line.charAt(level) == '#') {
            level++;
        }
        boolean isHeading = level > 0 && level < line.length() && line.charAt(level) == ' ';
        return isHeading ? level : 0;
    }

    private void flush(List<Chunk> blocks, Deque<String> path, StringBuilder buf) {
        if (buf.isEmpty()) {
            return;
        }
        blocks.add(new Chunk(String.join(" > ", path), buf.toString(), blocks.size()));
        buf.setLength(0);
    }
}
```

`splitLong` 按段落累加到阈值，实现省了。真实项目里还要处理表格、代码块和列表的完整性，不能从中间截断。

按语义切是另一条路：把文档拆成句子，算相邻句子的相似度，在相似度低谷处断开。听着合理，落地很麻烦。阈值调高块就碎，调低块就大，而且每句话都要过一次嵌入模型，索引成本翻几倍。我的判断是，企业文档先用结构切；语义切留给那些真的没有标题、没有编号、没有段落层次的纯文本，比如 OCR 出来的扫描件或者聊天记录导出。

切块这一步多半跑在异步流水线里，跟上传、解析、向量化一起排队，具体怎么拆开在 [Kafka 文档异步处理](https://blog.tooonran.top/2026/05/12/Kafka%20%E6%96%87%E6%A1%A3%E5%BC%82%E6%AD%A5%E5%A4%84%E7%90%86%EF%BC%9A%E4%B8%8A%E4%BC%A0%E3%80%81%E8%A7%A3%E6%9E%90%E3%80%81%E5%88%87%E5%9D%97%E3%80%81%E5%90%91%E9%87%8F%E5%8C%96%E6%80%8E%E4%B9%88%E8%A7%A3%E8%80%A6/) 那篇写过。

## 重叠窗口与父子块

重叠解决一个具体问题：一句话被切在两个块中间，两块各拿到半句。

比例上常见的是 10% 到 20%。512 的块配 64 或 100 的重叠，大部分跨句能兜住。再往上加，收益递减得很快。代价是实打实的：索引量按比例涨，嵌入调用跟着涨，检索时同一段文字可能出现在两个块里，占掉 topK 的两个位置，两个分数都不算高。

有个细节容易被忽略：重叠会把重复内容喂进 prompt。四个块里有两块内容重叠，模型相当于把同一句话读了两遍，长回答里偶尔会跟着复述。

值不值得，看边界是不是语义边界。按结构切的文档，一节就是完整的意思，边界本来就在该断的地方，重叠能省就省。按固定长度切的文档，边界纯粹是字符数决定的，重叠几乎是必须的。

小块召回准，但给模型的上下文不够；大块上下文够，向量又不够准。父子块就是把这两件事拆开。父块按结构切，通常是一节。子块在父块内部再按长度切，只索引子块，`metadata` 里带上 `parentId`。检索命中子块，再按 `parentId` 把父块取回来。

```java
// 命中子块后按 parentId 回填父块，父块数量单独限流
List<Document> children = vectorStore.similaritySearch(
        SearchRequest.builder().query(question).topK(12).build());

Map<String, List<Document>> byParent = children.stream()
        .collect(Collectors.groupingBy(d -> String.valueOf(d.getMetadata().get("parentId"))));

List<String> contexts = byParent.entrySet().stream()
        .limit(4)                                   // 12 个子块可能全来自同一个父块
        .map(e -> parentStore.get(e.getKey()))       // 父块单独存一份
        .filter(Objects::nonNull)
        .map(p -> truncate(p, 3000))                 // 截断也是一种降级，别省
        .toList();
```

父块存哪里都行，另一个 ES 索引、对象存储、Postgres 的 jsonb。关键是小块和大块要能对上，而且父块重建的时候子块索引得一起重建。坑在配额上：12 个子块很可能全来自同一节，按父块去重之后只剩一两个，白占了召回名额。所以取子块的时候 `topK` 要给得比需要的父块数大两三倍，去重之后再截断。

另一个坑是父块太大。四个父块各三千 token，加上系统提示和历史消息，一次请求就顶到窗口上限。父块的截断策略要提前想好，从哪截、截多少，别等线上报错再补。

## 结构化内容与元信息

表格被切开就没意义了。表头在一块里，数据行在另一块里，模型看到一列数字不知道每列是什么。

处理办法是整块保留。表格超过两千 token 的时候按行切，每块重复表头，并且在块开头写一句表名和单位。代码块同理，尽量按函数或类切，别从中间断开，元信息里带上文件路径和类名，检索到的时候模型至少知道这段代码属于哪。

扫描件是另一个麻烦。OCR 出来是一大段没有层次的文字，标题丢了，段落边界也糊了。这种情况退回固定长度，但页码必须带上，否则回答里给不出可核对的位置。一份文档里正文、表格、代码、附件混在一起很常见，切块器得先认块类型，再决定这一块怎么切。

元信息不只是给日志看的，它决定了检索能不能被约束。

| 字段 | 用途 | 例子 |
|---|---|---|
| `docId` | 去重、引用、回查原文 | `doc-2026-0412` |
| `chunkId` | 评测时精确标位置 | `doc-2026-0412-c07` |
| `sectionPath` | 拼进检索文本，补充语境 | `第3章 权限管理 > 3.2 数据归档` |
| `page` | 回答里给页码 | `12` |
| `updatedAt` | 判断答案是否过期 | `2026-04-12` |
| `acl` | 检索时过滤 | `dept:ops,role:admin` |
| `docType` | 按类型分派切块和提示 | `manual`、`contract` |

`sectionPath` 值得单独说。切块之后，块里往往只剩"超过 90 天的数据转冷存储"这样的句子，脱离了"归档"这个上下文。把章节标题拼在块的正文前面再向量化，`[第3章 权限管理 > 3.2 数据归档]` 这半句能把语境带回来。

`acl` 最容易被当成提示词处理。正确的做法是在检索阶段做过滤，ES 里就是一个 `filter` 条件，命中的文档本来就不该出现在候选里。只在 system prompt 里写"不要回答用户没权限查看的内容"，拦不住越权，也浪费召回名额。

## 切块质量的验证

改切块参数之前，先有一组固定的问题。40 条左右起步，每条标上文档、页码和小节，最好把答案的原文片段也存下来。有了这个，切块的好坏能落成几个数。

| 指标 | 怎么算 | 说明什么 |
|---|---|---|
| 命中率@8 | 前 8 条里含答案块的比例 | 整体召回水平 |
| 平均命中排名 | 答案块首次出现的位次 | 排序质量，比命中率敏感 |
| 边界失败占比 | 失败样本里答案跨块边界的比例 | 高就去调重叠和结构切分 |
| 块内答案完整率 | 人工看 20 条：块里有没有完整答案 | 区分"相关"和"能答" |
| 平均块 token | 索引里块的 token 均值 | 成本，也看分布是否离谱 |

`命中率` 涨了但 `块内答案完整率` 没动，多半是块变小了，召回变准但上下文不够，模型开始拼凑。边界失败占比是最有用的一项，它直接指向切法本身，不必在提示词上打补丁。评判还得看分布，不能看均值：一个 512 平均值的索引里，可能有一批 2000 token 的块，它们永远不会被排到前面，白占空间。

参数别写死在代码里。按文档类型分派、放进配置，改一次不用重新打包，跟 [Spring AI 模块化 RAG](https://blog.tooonran.top/2026/05/14/Spring%20AI%20%E6%A8%A1%E5%9D%97%E5%8C%96%20RAG%20%E5%AE%9E%E6%88%98%EF%BC%9A%E4%BB%8E%E6%89%8B%E5%8A%A8%E6%A3%80%E7%B4%A2%E5%88%B0%20Advisor%20%E7%AE%A1%E9%81%93%E7%9A%84%E6%BC%94%E8%BF%9B%E4%B9%8B%E8%B7%AF/) 里把 topK 收进 `app.rag.*` 是同一个思路。

## 总结

1. 切块是检索的上限。候选里没有的块，reranker 和更大的嵌入模型都补不回来。
2. 有结构的文档按结构切，固定长度做兜底，语义切块留给没有层次的纯文本。
3. 重叠买的是跨边界句子的完整性，按结构切时可以省，按长度切时不能省。
4. 父子块把"召回准"和"上下文够"拆成两步，代价是父块要单独存、要单独限流。
5. 评测要标到块和位置，否则改参数只能靠感觉。

这套参数是在六十份技术手册上试出来的，512 的块、64 的重叠、12 个子块取 4 个父块。换成合同或者扫描件，这几个数都要重调。切块这件事没有通用解，只有对着你的文档调出来的解。
