本地测试里跑一个四十来轮的长任务，第 34 轮时模型又调了一次 `read_file`，路径和第 12 轮那条一模一样。

工具照常执行，返回同样的内容，截断后写进 observation。模型这才接着往下走。

翻日志，前面还有几次重复：同一个目录列了两遍，同一份配置读了三次。工具结果堆到六万多 token，任务目标被挤到很远的位置，后面几轮它开始答非所问，说"已经完成"，其实中间两步没做。

窗口装得下，但它已经用不好了。

## 上下文构成与预算分配

Anthropic 讲上下文工程时提过一个现象，叫 context rot：窗口里的 token 越多，模型从中间取准信息的概率越低。换模型压不平这个趋势，只是陡缓不同。

占用率不是唯一指标，但它是少数能提前观测的。一次请求里大致是这几块：

| 组成 | 本地测试占比 | 能不能压 | 压的代价 |
|---|---|---|---|
| system prompt | 3%–5% | 基本不动 | 改坏了整轮行为都歪 |
| 工具定义 | 8%–12% | 按需挂载 | 工具少了模型会绕路 |
| 对话历史 | 10%–15% | 可摘要 | 用户的偏好最先丢 |
| 工具 observation | 50%–65% | 主要压这里 | 丢多了就重复调用 |
| 中间结果 | 5%–10% | 转存成引用 | 要额外的存储和读取 |
| 预留输出 | 10%–15% | 不能动 | 少了会被截断 |

大头是工具结果，而且它每轮都在涨。上一版的并行执行器（[一次并发 4 个工具调用：Agent 的并行执行引擎](https://blog.tooonran.top/2026/03/11/%E4%B8%80%E6%AC%A1%E5%B9%B6%E5%8F%91%204%20%E4%B8%AA%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8%EF%BC%9AAgent%20%E7%9A%84%E5%B9%B6%E8%A1%8C%E6%89%A7%E8%A1%8C%E5%BC%95%E6%93%8E/)一次回填四份结果，涨得更快，这块预算得按批算，按轮估会失真。

200k 的窗口我不会按 200k 排。实际按 90% 也就是 180k 算可用，输出预留 8k 到 16k，看单轮要写多少代码。剩下按块切：

| 块 | 配额 | 超了怎么处理 |
|---|---|---|
| system prompt + 工具定义 | ≤ 15% | 先砍工具，改成按需挂载 |
| 最近 6 轮原文 | 固定 | 不动，这是当前工作区 |
| 更早历史的摘要 | ≤ 10% | 旧摘要再摘要一次 |
| 工具 observation | ≤ 40% | 先截单条，再清老结果 |
| 预留 | ≥ 10% | 不许借 |

取舍顺序是固定的：截断单条超长结果 → 清掉老工具结果（保留调用记录本身）→ 压缩历史 → 最后才动用户最早说的那段话。

最后一步很少走。用户最早说的通常是任务目标，删了之后模型会把"做完的事"当成"要做的事"。

配额是软的，只用来决定先动谁。真正卡死的只有总数，到 90% 就必须做点什么。

并行批次要单独算。一批四个工具回来，瞬时占用是单次调用的四倍，按轮评估的预算表在这里会失真。我的做法是给批次结果加一条硬上限：单批回填总量不超过窗口的 15%，超了先截断，再考虑压历史。

每轮结束记一次 input_tokens，取最近十轮的滑动平均。单个峰值说明不了什么，持续爬升才要动手。真到了要动手那一步，第一个问题是压多早、留什么。

## 压缩触发与摘要取舍

70% 就开始压，丢掉的东西后面往往还要用。Claude Code 的压缩会留下架构决策、没解决的 bug、实现细节，丢掉重复的工具输出，这个取舍靠内容判断。压得越早，能拿来判断的信息越少，摘要质量越差。

太晚更麻烦。等模型已经开始重复调工具、开始答非所问，再拿这段历史去做摘要，等于在坏记录上做总结。

错的结论会被固化进摘要，后面几轮一直带着。

90% 是这两头之间挑的位置。窗口大小、输出预留、工具结果的平均长度都会挪动它，输出预留大的场景要往前提，不然压完发现放不下结果。

这个数没有权威出处，是按本地任务的窗口占用曲线调出来的。

触发之后剩下来的活是决定丢什么。四类信息不能丢：任务目标、已完成步骤、关键结论、未完成项。

约束也常被漏掉，漏了模型就敢改不该改的东西。模板大致长这样：

```json
{
  "goal": "把分页查询从 offset 改成 keyset",
  "constraints": ["不改对外接口签名", "兼容 MySQL 5.7"],
  "done": [
    {"step": "梳理 offset 调用点", "result": "7 处，3 处在定时任务里", "call_id": "call_3a"},
    {"step": "压测深度翻页", "result": "1 万条时 2.3s", "call_id": "call_71"}
  ],
  "findings": ["联合索引覆盖不了 (status, created_at)"],
  "open": [
    {"item": "定时任务里的 3 处怎么改", "blocked_by": "等确认能否加索引"},
    {"item": "回归用例", "blocked_by": null}
  ],
  "files_touched": ["PageQuery.java", "OrderJob.java"],
  "dropped": "第 5 轮到第 18 轮的工具原始输出"
}
```

`files_touched` 这条抄的是 Claude Code 的做法：压缩完把最近访问的几个文件一起带回来，比让模型自己回忆文件名靠谱。

`call_id` 先埋着，后面校验要用。

要求摘要模型输出 JSON 而不是散文，有个副作用：它会加字段。约束里写死"只许输出 schema 里的字段"，多出来的直接丢掉，别让它自由发挥。

## 切分边界与一致性

切历史是最容易出错的地方，也是重复调用最直接的成因。工具调用协议里，每个 tool_use 都要有一个 tool_result 用 id 对回去，而且整批结果必须放进同一条 user 消息。压缩切点如果落在中间，模型看到的是一个没有回答的调用，它会怎么办？再调一次。

```text
历史下标（每条消息一行）:

  11  user      : 看下配置文件 app.yml
  12  assistant : tool_use(read_file, path=app.yml)
  13  user      : tool_result = <全文 4k token>
  14  assistant : ...

候选切点:
  A. 12 和 13 之间  错，留下没有结果的调用
  B. 11 和 12 之间  对，调用和结果都在同一侧
  C. 13 和 14 之间  对

规则: 切点只能落在"消息组"边界。
消息组 = 一条 assistant 消息里的 tool_use 块
       + 下一条 user 消息里的全部 tool_result 块。
并行批次同理，四个 tool_use 和四个 tool_result 是一整组。
```

实现上不用做复杂对齐。按消息组从后往前数，够 6 轮就停，剩下的整体交给压缩器。别按 token 数硬切，一刀切在组中间，后面几轮全乱。

摘要由模型生成，它会把"改了三处"写成"改完四处"。压完立刻校验一次，比事后排查便宜得多。

我不做语义比对，太贵也不准。只做四类机械检查：

| 检查 | 触发条件 | 处理 |
|---|---|---|
| goal 为空 | 摘要里没这个字段 | 用第一条用户消息补上 |
| goal 撞不上原文 | 和首条用户消息字符交集为空 | 直接覆盖成原文 |
| done 的 call_id 不存在 | 对不上历史里的 tool_use | 删掉该项 |
| open 为空但任务没完 | 最近两轮还有未完成的工具调用 | 把最近两轮原文附在摘要后 |

最后一条救过几次。摘要模型有个倾向：写到结尾想把活儿收掉，于是 open 那栏空着，看着像任务已经结束。这四条加起来不到五十行代码，但能拦住大部分坏摘要。

摘要之外还有一条路：大块中间结果落到文件里，上下文里只留路径和一行说明。这样压缩只压对话，不压产物。模型要细节的时候用工具去读，读多少由它决定，比"全部塞进摘要"灵活，也比"全部丢掉"安全。

代价是需要额外的读取轮次，而且路径得稳定。产物类文件我按 `runs/<runId>/<step>/` 归位，引用里带时间戳，避免读到上一版。

不是所有东西都值得落盘。查一次天气的结果没人会再看，摘要一行就够。判断标准是这个结果后面还会不会被读，会就落盘，不会就压掉。

## 成本与延迟收益

同一批本地任务，改前改后的对比：

| 指标 | 不压缩 | 90% 触发压缩 |
|---|---|---|
| 单轮请求 token 峰值 | 182k | 96k |
| 累计输入 token | 约 4.1M | 约 2.6M |
| 重复工具调用次数 | 11 | 3 |
| 跑到结束的轮数 | 47 | 39 |
| 端到端耗时 | 21 分钟 | 15 分钟 |

两列在同一台机器、同一个模型、同一批任务上测的，换个任务分布数字会变。说清楚一点，这组数字里有一部分不属于压缩。我在同一版里改了工具结果的截断策略，单条从全量回填改成 2k token 上限加首尾摘要。压缩本身的贡献大概占一半，具体多少我没拆干净。压缩自己要花一次模型调用，几秒钟、几万 token，任务越长摊得越薄。

还有个反直觉的地方：省 token 不是目的。压得太狠，模型多跑八轮，账是亏的。所以我看这块的指标顺序是重复调用次数、总轮数、最后才是 token。

## 总结

1. 大头在工具 observation，压缩先动它。system prompt 和用户最早那段话是最后才碰的。
2. 触发点定在 90%，是给摘要留判断余量。太早压丢信息，太晚压等于在坏历史上总结。
3. 切点只能落在消息组边界，tool_use 和 tool_result 不能分家，切开就会被重新调用。
4. 压完只做机械校验，四条够用：goal 为空、goal 撞不上原文、done 对不上 call_id、open 空着但任务没完。
5. 评估压缩效果先看重复调用次数和总轮数，光看 token 会得出错误结论。
